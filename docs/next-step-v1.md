## 2. 판단 3단계

약속 문서의 판단 순서는 `규칙 → 저장된 길 → 앱 지식 표 → AI → 검사 층`이다. 이 중 **저장된 길과 AI**를 3단계로 나눈다.

- 규칙 · 앱 지식 표 · 검사 층 · 멈춤 규칙은 Guide 담당이다.
- 어느 단계의 답이든 검사 층을 거쳐서 나간다.
- **어느 단계를 쓸지는 Guide가 정한다.** AI는 답과 확신도만 준다.

| 단계 | `source` | 넣는 것 | 다음 단계로 넘기는 경우 |
|---|---|---|---|
| **1. 저장된 경로** | `CACHE` | 화면 지문 + 업무 종류<br>(Redis `path:{fingerprint}:{taskType}`) | 저장된 길 없음 · `STALE`<br>저장된 칸을 지금 화면에서 못 찾음<br>사람마다 답이 다른 단계 (받는 사람 · 가게 · 역)<br>`bigMode`가 다름<br>다른 화면에 갔다 돌아옴 (v0.2 ⓕ) |
| **2. 가벼운 모델** | `AI_TEXT` | 후보 목록 (번호 · 글자 · 역할 · selected)<br>+ 목표 + 앱 지도 | 확신도 < **0.70**<br>AI가 `NEED_IMAGE`<br>고른 후보 글자가 빈칸<br>형식 오류 · 없는 번호 2번 |
| **3. 글자 보완** | `AI_TEXT` | 2단계 입력 + 폰 안 OCR 글자 (`src: "OCR"`) | 확신도 < **0.50**이면 멈춤 |
| 3-옵션. 사진 + 큰 모델 | `AI_IMAGE` | 2단계 입력 + 가린 스크린숏 | **나중 옵션** (동의 받고 켬) |

> **참고**
> - 후보 중 글자 없는 칸이 **50% 이상**이면 2단계를 건너뛰고 바로 3단계로 간다.
> - 3단계로 갈 때는 서버가 `needOcr: true`를 주고, 앱이 OCR 글자를 넣어 다시 보낸다. 앱 왕복이 1번 늘어난다.
> - 1단계에서 찾은 칸의 위치는 저장된 값이 아니라 **지금 화면에서 찾은 칸의 값**을 쓴다.

## 3. 서버 ↔ AI 입력 · 출력

Guide가 앱이 보낸 `elements[]`에서 후보를 골라 AI에 넘기고, AI는 **후보 번호 하나(`pick`)만 고른다.** Guide가 그 번호의 실제 칸 위치 · 글자로 바꿔 검사한다. AI는 좌표를 지어낼 수 없다.

칸 이름은 시제품 `brain.py`의 JSON 스키마를 약속 문서 이름 규칙(camelCase)에 맞췄다.

### 3-1. 요청 (Guide → AI)

```json
{
  "purpose": "NEXT",
  "mode": "TEXT",
  "goal": "사진 보내기: 받는 사람 [이름1], 사진 2장",
  "taskType": "SEND_PHOTO",
  "slots": { "RECIPIENT": "[이름1]", "COUNT": 2 },
  "app": { "package": "com.kakao.talk", "versionCode": 11020000, "bigMode": false },
  "appMap": "카카오톡. 채팅 탭에 대화방 목록. 대화방 아래 + 버튼 → 앨범. 사진은 어르신이 고른다. 전송부터는 STOP.",
  "history": [ { "screen": "카톡 첫 화면", "action": "TAP", "label": "채팅" } ],
  "candidates": [
    { "idx": 1, "text": "채팅",        "role": "TEXT",   "selected": true,  "ban": null },
    { "idx": 2, "text": "[이름1]",     "role": "BUTTON", "selected": false, "ban": null },
    { "idx": 3, "text": "[이름2]",     "role": "BUTTON", "selected": false, "ban": null },
    { "idx": 4, "text": "가족 단톡방", "role": "BUTTON", "selected": false, "ban": null },
    { "idx": 5, "text": "",            "role": "BUTTON", "selected": false, "ban": null, "src": "ACC" }
  ],
  "infoTexts": ["채팅"]
}
```

| 칸 | 뜻 |
|---|---|
| `mode` | `TEXT` = 글자만 (2 · 3단계). `IMAGE`는 사진 옵션을 켰을 때만 |
| `goal` | 목표를 한 줄로. slots를 풀어 쓰고, 이미 끝낸 칸도 적는다 (시제품 `goal_of()`) |
| `appMap` | 앱 지도. 규칙이 아니라 AI에게 주는 힌트 (시제품 `APP_MAP`) |
| `history` | 이번 안내에서 지금까지 고른 것. 최근 몇 개만 (Redis 세션) |
| `candidates[].idx` | **약속 문서 `elements[].idx` 그대로.** AI는 이 번호로 `pick` |
| `candidates[].selected` | v0.2. `null`이면 모름 |
| `candidates[].ban` | 금지 버튼이면 이유 (예: 「금지 단어 '전송'」). 시제품의 ⛔ 표시 |
| `candidates[].src` | `ACC` (접근성) · `OCR` (3단계) |
| `infoTexts` | 누를 수 없는 제목 · 안내 글자 |

> **좌표(`bounds`)는 AI에 넘기지 않는다.**
> 후보 고르기 (배경 칸 빼기, 글자 없는 작은 아이콘 빼기, 칸 안 글자 합치기)는 시제품 `candidates()`처럼 Guide가 한다.

### 3-2. 응답 (AI → Guide)

```json
{
  "progress": "맞음: 앱 열기 / 남음: 받는 사람 · 사진 · 전송",
  "action": "TAP",
  "pick": 2,
  "scroll": null,
  "reason": null,
  "confidence": 0.93,
  "why": "받는 사람 [이름1]과 같은 글자의 후보가 2번 하나뿐",
  "expectNext": "[이름1] 대화방이 열리고 아래에 + 버튼과 입력창이 보임"
}
```

| 칸 | 뜻 | 시제품 `brain.py`와 비교 |
|---|---|---|
| `progress` | 채워진 칸 · 남은 칸을 **맨 먼저** 적는다 (40자 이내) | 같음. 빼면 23/24 → 21/24 |
| `action` | 3-4의 값만 | 같음 |
| `pick` | 고른 후보 번호 (`candidates[].idx`). `TAP` · `TYPE`일 때만, 그 밖엔 `null` | `"c2"` → 숫자 `idx`로 (6절 ①) |
| `scroll` | `SCROLL`일 때 `{ "dir": "next" }`. `next` · `prev` · `left` · `right` | `scroll_dir: down/up` → 약속 문서 이름으로 (6절 ②) |
| `reason` | `PICK_BY_USER` · `WAIT`일 때 이유 | 없음 → 추가 |
| `confidence` | 0~1. Guide가 4절 기준값과 비교한다. **앱으로는 안 나가고** `AI_CALL`에 기록 | 같음 |
| `why` | 고른 이유 한 줄. 로그 전용 | 같음 |
| `expectNext` | 누르면 나올 화면 예측 한 줄. 잘못 누름 · 엉뚱한 화면 알아채기에 씀 | `expect_next` |

> **참고**
> - `say` (말풍선 문장)는 **AI가 쓰지 않고 Guide가 템플릿으로** 만든다고 둔다 (약속 문서 2절 원칙). 시제품은 AI가 쓴다 → 6절 ③.
> - `why` · `progress` · `expectNext`는 로그용이지만 **정확도에도 영향이 있다.** 시제품 측정: 긴 답 23/24 · 4.0초, 짧은 답 21/24 · 3.3초. 그래서 v1은 긴 답으로 둔다.

### 3-3. 앱에 나가는 칸을 누가 채우나

| 앱 응답 칸 | 채우는 쪽 | 어떻게 |
|---|---|---|
| `action` · `scroll` · `reason` | AI | 3-2 그대로 |
| `target` (idx · label · bounds · viewId · fingerprint) | Guide | **`pick`으로 `elements[]`에서 그 칸을 꺼낸다.** 검사 층은 이 실제 칸 글자로 금지 버튼을 검사 |
| `skill` | Guide | 앱 지식 · 체크리스트에서 |
| `say` | Guide | 템플릿 |
| `sessionId` · `stepId` · `source` · `needOcr` · `needScreenshot` · `elapsedMs` · `deeplink` | Guide | |

### 3-4. AI가 쓰는 `action`

| AI가 씀 | Guide만 씀 |
|---|---|
| `TAP` · `TYPE` · `SCROLL` · `BACK` · `WAIT` · `PICK_BY_USER` · `DONE` · `NEED_IMAGE` | `STOP` (멈춤 규칙) · `ASK` (되묻기 규칙) · `OPEN_DEEPLINK` (앱 지식) · `GIVE_UP` ('안 돼요' 횟수) |

- **`NEED_IMAGE`**: 글자만으로 판단이 안 된다는 뜻. Guide가 `needOcr: true` (사진 옵션이 켜져 있으면 `needScreenshot: true`)로 바꿔 앱에 보낸다. 앱으로는 나가지 않는 AI 전용 값.
- **`BACK`**: 엉뚱한 화면이면 뒤로. 시제품에 있고 약속 문서 `action` 표에는 없다 → 6절 ④.
- **`STOP` · `ASK`**: 시제품은 AI도 쓴다. v1에서는 AI가 써도 Guide가 최종 판단한다 (「멈춤 규칙은 서버가 최종 확인, AI 답보다 우선」).
- **형식 오류**: 형식이 틀리거나, `pick`이 후보에 없거나, `ban` 후보를 고르면 시제품처럼 **이유를 알려 주고 한 번 더** 묻는다. 또 틀리면 `AI_BAD_OUTPUT`.

## 4. 확신도 기준값

2.1.7 동작 흐름 v1.1의 **5 (판단)** · **11 (정지)**에서 쓰는 값이다.

| 쓰는 곳 | 기준값 (v1 임시) | 뜻 |
|---|---|---|
| 5 판단 | `confidence < 0.70` | 2단계 답을 버리고 3단계 (OCR 글자 보완)로 |
| 11 정지 | `confidence < 0.50` | 3단계 답도 버리고 멈춤. 「이 화면은 잘 모르겠어요」 |
| 2단계 건너뛰기 | 글자 없는 후보 ≥ 50% | 바로 3단계 |

**확신도와 상관없이** 넘기거나 멈추는 경우

- `NEED_IMAGE`
- 고른 후보 글자가 빈칸
- 형식 오류 · 없는 번호 · 금지 후보 2번
- 금지 버튼 · 화면 아래 돈 버튼 (→ `STOP`)

> **왜 확신도만 믿지 않나**
> 모델이 스스로 매긴 확신도는 실제 정답률과 잘 안 맞을 수 있다. 그래서 위의 확실한 신호를 같이 쓴다.

> **기준값 확정 방법**
> 기준 2 채점 때 정답셋 10건의 `confidence`를 같이 기록한다. 맞힌 건과 틀린 건이 갈리는 지점으로 0.70 · 0.50을 다시 정한다. 시제품 `brain_eval` 24화면 결과에도 확신도를 더해 같이 본다.

## 5. 사람이 고르는 화면 규칙

### 5-1. 무엇을 가르나

누르는 건 항상 어르신이다. 여기서 가르는 건 **누를 버튼을 누가 정하나**다.

| | AI가 정함 (`TAP`) | 어르신이 정함 (`PICK_BY_USER`) |
|---|---|---|
| 기준 | 어르신 요청만으로 누를 버튼이 **하나로 정해짐** | 요청만으로는 안 정해지거나, **본인이 결정할 일** |
| 화면 표시: 오버레이만 | 버튼 하나에 동그라미만 | 아무것도 안 뜸 |
| 화면 표시: 오버레이 + 설명 | 버튼 하나에 동그라미 + 「이걸 눌러 주세요」 | 동그라미 없이 설명만 「보낼 사진을 골라 주세요」 |
| 예 | 「민지한테 보내줘」 + 채팅 목록에 「손녀 민지」 하나 | 「아까 찍은 사진 두 장」 + 갤러리에 사진 수십 장 |

> **참고**
> - 화면 표시 모드 (「오버레이만」 / 「오버레이 + 설명」)는 어르신이 설정에서 고른다. 서버 응답은 모드와 상관없이 같고, 무엇을 보여 줄지는 앱이 정한다.
> - 결제 · 인증 (`STOP`)은 Guide 멈춤 규칙이 따로 처리한다. 정답셋의 「위험 화면」 칸과도 별개다.

### 5-2. 규칙 v1

위에서부터 보고 **처음 맞는 규칙 하나**로 정한다.

| # | 화면 | 알아보는 신호 | 결과 | 어디서 처리 |
|---|---|---|---|---|
| R1 | 권한 창 | 패키지가 `permissioncontroller`, 또는 「허용」 · 「허용 안함」 · 「앱 사용 중에만 허용」 버튼 | `PICK_BY_USER(PERMISSION)` | Guide 규칙 층 |
| R2 | 약관 · 동의 | 「동의」 · 「약관」 · 「개인정보 수집」 글자 + 체크 칸 | `PICK_BY_USER(CONSENT)` | Guide 규칙 층 |
| R3 | 확인 창 | 버튼 2개짜리 창 (「확인/취소」 · 「예/아니오」)이고 본문이 「~할까요?」 | `PICK_BY_USER(CONFIRM_DIALOG)` | Guide 규칙 층 |
| R4 | 좌석 고르기 | 좌석 배치 화면 (글자 없는 작은 칸이 격자로 많음, 「좌석」 제목) | `PICK_BY_USER(SEAT)` | AI 프롬프트 |
| R5 | 사진 · 파일 고르기 | 사진 격자 (`IMAGE` 칸이 많음, 「앨범」 · 「사진」 · 「갤러리」 제목) | `PICK_BY_USER(PHOTO)` | AI 프롬프트 |
| R6 | 요청 값이 화면에 여러 개 | slots 값 (예: RECIPIENT)과 같은 글자의 후보가 2개 이상 | `ASK` 「어느 ○○이에요?」 | AI 프롬프트 → Guide |
| - | 그 밖 | 요청 값과 맞는 후보가 하나 | `TAP` + `pick` | AI |

- **R5는 v1에서 항상 넘긴다.** 「방금 찍은 사진 한 장」처럼 정해져 보여도, 잘못 고르면 다른 사람에게 사진이 가서 되돌리기 어렵다.
- **R1~R3은 Guide 규칙 층에서 먼저 걸러진다.** 화면 글자만으로 알 수 있어서 AI까지 가지 않는다. 비용 0원.
- 말로 답할 수 있는 것 (날짜 · 인원)은 `ASK`, 화면을 봐야 고를 수 있는 것 (사진 · 좌석)은 `PICK_BY_USER`.

### 5-3. 정답셋에서 세는 방법

5.6.2 정답셋 시트에 칸 2개를 더한다.

| 더할 칸 | 채우는 법 |
|---|---|
| **사람이 고름 (정답)** | 줄마다 사람이 보고 「AI가 골라도 되나?」를 판단. 안 되면 `예` + reason |
| **규칙 결과** | 5-2 규칙을 그대로 적용한 결과. `예(R5)` · `아니오`처럼 몇 번 규칙인지까지 |

**결과표** (1번 줄만 채운 틀)

| 번호 | 화면 | 어르신 요청 | 사람이 고름 (정답) | 규칙 결과 | 맞음 |
|---|---|---|---|---|---|
